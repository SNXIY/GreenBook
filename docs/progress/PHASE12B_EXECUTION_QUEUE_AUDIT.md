# Phase 12-B Execution Queue Audit

## Scope

This audit follows the current production-shaped request path from the
Assistant API to `RuntimeAgentService`, `ExecutionWorker`, the execution
repository, and the event store. It also checks the standalone Assistant
worker and existing queue/storage capabilities.

The audit does not change Planner, TaskProvider, TaskOrchestrator, Creator,
Java, or Frontend behavior.

## Current request path

The normal Runtime message route is:

```text
POST /api/v1/assistant/conversations/{conversation_id}/messages
  -> _send_runtime_message()
  -> ConversationRuntimeAdapter.execute(detach=False)
  -> RuntimeAgentService.execute()
  -> RuntimeAgentService._execute_single()
  -> Planner / validation
  -> ExecutionWorker.init_from_plan()
  -> ExecutionStateManager.init_execution()
  -> ExecutionRepository.save()
  -> ExecutionWorker.run(execution_id)
  -> ToolRuntime / MCP tool calls
  -> EventStore + ExecutionRepository state updates
  -> RuntimeResult / HTTP response
```

`ConversationRuntimeAdapter` does not pass `detach=True` from the normal HTTP
message route. `RuntimeAgentService.execute()` therefore follows its direct
path. The service constructs the `CapabilityExecutor`, `ToolRuntime`, and
`ExecutionWorker` in the API process, creates the `PlanExecution`, and then
awaits `worker.run()` in the same request task.

There is an additive detached API in `AssistantService.execute_background()`
and a `detach` option in `RuntimeAgentService`, but that path only moves the
same Worker pass to an API-owned `asyncio.Task`. It is not a separate process
queue and does not survive API restart.

## Answers to the audit questions

### 1. Where is the Execution created?

The `ExecutionWorker.init_from_plan()` adapter creates a `TaskPlan` from the
validated `ExecutablePlan` and calls `ExecutionStateManager.init_execution()`.
The state manager builds `PlanExecution` and `StepExecution` models and saves
them through the injected `ExecutionRepository`.

With the Phase 11-E wiring, the repository may be the PostgreSQL adapter, but
the creation still happens inside the API process during the service call.

### 2. Where does execution start?

Immediately after creation, `_execute_single()` calls
`ExecutionWorker.run(execution.execution_id)`. The Worker starts the execution
state and invokes the capability/tool path. For detached mode, the same call
is scheduled as an API-local `asyncio.Task`; it is not claimed by
`apps/assistant_worker`.

### 3. Does the API wait for execution?

Yes for the normal message route. The route awaits the adapter, which awaits
`RuntimeAgentService`, which awaits `ExecutionWorker.run()`. The HTTP response
is returned after the current Worker pass reaches a result such as completed,
failed, approval-required, or asynchronous-tool waiting.

The detached compatibility path returns earlier, but its execution remains
owned by the API process and is lost on process restart.

### 4. When is `execution_id` returned?

`execution_id` is generated by `PlanExecution` when
`ExecutionStateManager.init_execution()` is called. The service assigns it to
the `RuntimeContext`, trace, and executor immediately afterward. The normal
HTTP response returns it only after the Worker pass has completed. The
detached path returns it after creation, before its API-local Worker task
finishes.

### 5. Does a queue capability already exist?

There is no generic Execution Queue abstraction, Redis adapter, or Redis
dependency.

Existing related capabilities are narrower:

| Capability | Exists | Scope |
| --- | --- | --- |
| `RetryTaskStore` | Yes, memory/PostgreSQL | Delayed retry tasks only |
| `RetryScheduler` | Yes | Claims retry tasks and prepares retry transitions |
| `RetryBackgroundWorker` | Yes | Runs the retry task consumer in the standalone worker |
| `ExecutionLeaseManager` | Yes, memory/PostgreSQL | Lease primitive; no normal Execution consumer yet |
| Kafka | Dependency declaration only | No Runtime Execution consumer is wired |
| Redis | No | No adapter or lifecycle wiring found |

The minimal queue implementation can therefore reuse the existing
PostgreSQL persistence bind and lease/claim conventions without introducing
Kafka or Redis.

### 6. Which code must move to a worker?

The separate worker must own the execution side after a durable queue claim:

- queue claim/lease lifecycle;
- loading the persisted execution dispatch record;
- constructing the process-local MCP/Creator/Java execution adapters;
- `ExecutionWorker.run()` and continuation handling;
- tool invocation, evidence recording, failure decision, retry scheduling,
  and event/state persistence;
- ack on a terminal/handled queue result, or release/fail on an unhandled
  worker error.

The API should retain request-scoped work needed to authenticate and resolve
the request, compile the Task context, produce and validate the plan, create
the canonical `PlanExecution`, and enqueue its id.

## Cross-process execution gap

An `execution_id` alone is not currently sufficient to reconstruct the API's
execution closure in a new process. `PlanExecution` persists step metadata and
checkpoint constraints, but not the complete values currently held only in
memory:

- serialized `RuntimeContext` and `TaskContext` snapshot;
- lossless `IntentSpec` / `PlanningContext` used by argument binding;
- the validated `ExecutablePlan` details needed to rebuild the executor;
- conversation/session inputs used by MCP tools;
- a safe authorization/credential reference for downstream Java calls;
- the API-only result projection callback and in-memory run store.

The verified `AuthContext.raw_access_token` must not be written to a durable
queue payload. A production worker therefore needs a credential-reference or
service-authorization contract before it can safely relay a user's identity
to Java. This phase's queue contract must keep that concern explicit rather
than silently serializing a bearer token.

## Required queue boundary

The queue itself should remain business-neutral:

```text
API
  -> create PlanExecution
  -> persist dispatch envelope
  -> enqueue execution_id

Worker
  -> claim execution_id
  -> load dispatch envelope
  -> invoke an injected execution handler
  -> ack / fail / release
```

The queue must not call Planner, MCP, Java, Creator, or `ExecutionWorker` on
its own. The handler boundary makes the queue testable and allows the
execution-context/credential contract to be completed without coupling queue
storage to business logic.

## Audit conclusion

The current API path is synchronous because Execution creation and Worker
execution are one service method. A durable `ExecutionQueue` plus a
worker-owned consumer is the correct next boundary. Queue storage can reuse
the existing PostgreSQL persistence profile, while execution dispatch data
and secure worker authorization must be treated as separate concerns from the
queue message identity.
